## 1. 概述

### 1.1 目标

在 Android 平台上实现一套**完整、可靠、全场景**的 GPS 轨迹记录系统，满足：

- **步行**：保留转弯细节，不被过度简化
- **骑行**：红绿灯起步/停车能正确响应
- **驾车**：高速场景下不被过密采样
- **静止**：拒绝 GPS 漂移点，不产生"噪声轨迹"

### 1.2 场景

| 场景 | 记录时长 | 典型速度 | 采样频率 |
|---|---|---|---|
| 步行 | 30 分钟 | 0.5-1.5 m/s | ~1 Hz |
| 骑行 | 1 小时 | 3-8 m/s | ~1 Hz |
| 驾车 | 数小时 | 15-30 m/s | ~1 Hz |
| 静止 | 数十分钟 | 0 m/s | ~1 Hz |

### 1.3 与其他模块的关系

```
┌───────────────────────────────────────┐
│  LocationTracker（位置追踪）           │
│  ├─ 过滤管线 → 显示位置                 │
│  └─ 原始 fix → TrackRecorder（本模块） │
└───────────────────────────────────────┘
                    ↓
┌───────────────────────────────────────┐
│  Track（轨迹记录）                     │
│  ├─ TrackFilter      入口过滤（漂移）  │
│  ├─ TrackRecorder    内存累积          │
│  ├─ TrackSimplifier  存储简化          │
│  ├─ TrackStore       文件读写          │
│  └─ TrackPlayer      回放              │
└───────────────────────────────────────┘
```

**关键点**：轨迹记录**独立于位置显示管线**。位置显示经过位置过滤（低通、卡尔曼），而轨迹记录采用**原始 GPS fix**——这保证轨迹保留真实形状。

## 2. 核心设计原则

### 2.1 两阶段处理

```
原始 fix
   ↓
【阶段 1：入口过滤】← 每次 fix 时判定，拒绝漂移点
   ↓
保留点
   ↓
【阶段 2：存储简化】← stop 时一次性简化
   ↓
最终轨迹文件
```

**为什么分两阶段？**

| 阶段 | 目的 | 时机 | 复杂性 |
|---|---|---|---|
| 入口过滤 | 剔除无效点 | 实时 | 低（逐点判定） |
| 存储简化 | 压缩冗余点 | 停止时 | 高（需全局视角） |

分开的好处：
- **实时阶段轻量**：不拖累 fix 处理
- **离线阶段精细**：Douglas-Peucker 需要看整条轨迹才能决定哪些点可删

### 2.2 记录原始 fix，不做位置平滑

位置显示管线会对 fix 做：
- 低速低通（静止时几乎不动）
- 卡尔曼滤波（速度融合）
- Dead Reckoning（隧道推算）

**轨迹记录跳过这些**，因为：

| 处理 | 对显示有利 | 对轨迹有害 |
|---|---|---|
| 低速低通 | 消除停车抖动 | 抹平真实小范围运动（如停车场绕圈） |
| 卡尔曼滤波 | 平滑速度值 | 改变位置轨迹的形状 |
| Dead Reckoning | 隧道内保持显示 | 推算位置不是实测轨迹 |

因此轨迹只经过 `TrackFilter`（拒绝无效点），不做任何**位置平滑**。

### 2.3 状态与逻辑分离

- `TrackRecorder`：纯记录器，不关心何时启动/停止
- `LocationTracker`：控制何时开始/停止记录
- `MapLibreMapView`：通过 Compose 参数驱动状态

**好处**：任何一层都可以独立测试、替换。

## 4. 数据结构

### 4.1 TrackPoint

```kotlin
data class TrackPoint(
    val lat: Double,
    val lng: Double,
    val altitudeM: Double?,
    val speedMps: Float?,
    val bearingDeg: Float?,
    val accuracyM: Float?,
    val timestampMs: Long,     // 墙钟时间戳
    val elapsedNanos: Long,    // 单调时钟（用于回放时间轴）
)
```

**字段说明**：

| 字段 | 类型 | 来源 | 用途 |
|---|---|---|---|
| `lat` / `lng` | Double | `Location.getLatitude/Longitude` | 位置 |
| `altitudeM` | Double? | `Location.getAltitude` | 海拔（可选） |
| `speedMps` | Float? | `Location.getSpeed` | 速度（可选） |
| `bearingDeg` | Float? | `Location.getBearing` | 方向（可选） |
| `accuracyM` | Float? | `Location.getAccuracy` | 精度（可选） |
| `timestampMs` | Long | `System.currentTimeMillis` | 显示时间 |
| `elapsedNanos` | Long | `Location.getElapsedRealtimeNanos` | 回放时间轴 |

**为什么需要两个时间戳？**

- `timestampMs`（墙钟）：用户看到的日期/时间，可能因 NTP 同步跳变
- `elapsedNanos`（单调）：回放时的真实时间间隔，不受用户改时间影响

回放用 `elapsedNanos` 计算帧间隔，避免"用户改了系统时间导致回放快进"。

### 4.2 空值处理原则

除 `lat` / `lng` / 时间戳外，其他字段都可能为 `null`：

- `Location.hasAltitude()` 返回 false → `altitudeM = null`
- `Location.hasSpeed()` 返回 false → `speedMps = null`
- `Location.hasBearing()` 返回 false → `bearingDeg = null`
- `Location.hasAccuracy()` 返回 false → `accuracyM = null`

CSV 用**空字段**表示 `null`（详见 §8）。

## 5. 轨迹过滤器（TrackFilter）

### 5.1 设计目标

**核心矛盾**：

- **拒绝漂移**：GPS 静止时会有 ±5-15 m 的随机跳动，若全部记录会产生大量"噪声点"
- **不误杀真实移动**：步行时每秒移动 1-1.5 m，若过度过滤会丢点

**解决思路**：多层规则，逐级判定。

### 5.2 六条规则

按顺序判定，任一条返回 `false` 立即拒绝。

#### 规则 1：精度门控

```kotlin
if (accuracyM != null && accuracyM > maxAccuracyM) return false
```

**原理**：`accuracyM` 是 GPS 报告的精度半径（68% 置信度）。超过 40 m 说明信号极差，位置不可信。

**默认值**：`maxAccuracyM = 40f`

**副作用**：城市峡谷、室内、桥下会丢点。可调高（60-80）换取更多覆盖。

#### 规则 2：首点必收

```kotlin
if (lastKept == null) return true
```

**原理**：第一个点无条件记录，作为后续判定的基准。

#### 规则 3：物理可能性

```kotlin
val plausible = 30.0 * dtSec + 35.0
if (dist > plausible) return false
```

**原理**：从上一个保留点到候选点，移动距离超过物理可能（30 m/s ≈ 108 km/h + 35 m GPS 波动余量）则拒绝。

**为什么是 30 m/s？**
- 一般道路最高限速 120 km/h ≈ 33 m/s
- 加上 GPS 误差裕量
- 若真在高铁/飞机上，会被误拒——但那不是本系统的目标场景

#### 规则 4：静止漂移抑制

```kotlin
if (reportedSpeed < stillSpeedMps && dist > driftDistanceM) {
    // 判定为漂移候选
    if (nearPreviousDrift) driftStreak++
    else { driftStreak = 1; driftLat = ...; driftLng = ... }
    
    if (driftStreak >= driftStreakToAccept) {
        // 连续 3 次同一区域 → 接受
        return true
    }
    return false
}
```

**原理**：速度接近 0，但位置移动超过阈值 → 疑似漂移。

**自愈机制**：连续 3 次在同一区域（15 m 内），说明不是随机漂移，而是**真实移动**（比如起步时 GPS 速度还没跟上），接受。

**关键参数**：
- `stillSpeedMps = 0.5f`：低于此速度算"静止"
- `driftDistanceM = 8.0`：超过此距离触发漂移判定
- `driftStreakToAccept = 3`：连续 N 次接受
- `driftZoneM = 15.0`：判定"同一区域"的半径

**为什么静止时也会真移动？**
- 用户在等红灯时轻微挪动
- 手机放在口袋里晃动
- 停车后走动
- 3 次连续漂移共约 3 秒，如果这 3 秒都在同一小区域，值得记录

#### 规则 5：运动开始锚点

```kotlin
if (lastKeptSpeedMps < 0.3f && reportedSpeed >= 1.0f && dist > 3.0) {
    return true
}
```

**原理**：从上一次**静止**（速度 < 0.3 m/s）到现在**移动**（速度 ≥ 1.0 m/s），即使距离很小也保留——这是运动的起点，有轨迹价值。

**场景**：用户在停车位启动车辆，前 3 秒移动 5 m——虽然距离小，但这是运动的起点。

#### 规则 6：自适应最小距离

```kotlin
val adaptiveMinDist = maxOf(
    1.0,                        // 最低 1 米
    0.5 * reportedSpeed * dtSec, // 速度的一半 × 时间
    (accuracyM ?: 0f) * 0.3,     // 精度的 30%
)
if (dist < adaptiveMinDist) return false
```

**原理**：三点取最大作为最小距离阈值。

- **1 m**：绝对下限，防止原地反复记录
- **0.5 × speed × dt**：速度的一半乘以时间间隔，慢速时允许更密，快速时自动稀疏
- **0.3 × accuracy**：精度差的点需要更大间隔才记录（精度 10 m → 阈值 3 m；精度 30 m → 阈值 9 m）

### 5.3 状态机

```
                  ┌─────────────┐
                  │  初始状态    │
                  └──────┬──────┘
                         │ 首点
                         ▼
                  ┌─────────────┐
        ┌────────►│  正常记录    │◄────────┐
        │         └──────┬──────┘         │
        │                │                │
        │ 运动开始        │ 静止漂移        │ 距离足够
        │ (规则 5)       │ (规则 4)        │ (规则 6)
        │                ▼                │
        │         ┌─────────────┐         │
        └─────────│  漂移判定    │─────────┘
                  │ driftStreak │
                  └──────┬──────┘
                         │ 连续 3 次
                         ▼
                  ┌─────────────┐
                  │  确认为真    │
                  │  实移动      │
                  └─────────────┘
```

### 5.4 参数与场景

| 参数 | 步行 | 骑行 | 驾车 |
|---|---|---|---|
| `maxAccuracyM` | 40 (松) | 40 (中) | 30 (严) |
| `stillSpeedMps` | 0.3 | 0.5 | 1.0 |
| `driftDistanceM` | 5.0 | 8.0 | 15.0 |
| `driftStreakToAccept` | 2 | 3 | 3 |

## 6. 轨迹记录器（TrackRecorder）

### 6.1 生命周期

```
start(nameHint)
   │
   ├─ buffer = mutableListOf()
   ├─ filter.reset()
   └─ targetFile = TrackStore.newFile(dir, nameHint)
   │
   ▼
record(loc)  ← 每个 GPS fix 调用
   │
   ├─ 构建 TrackPoint
   ├─ filter.shouldKeep()
   └─ 通过 → buffer.add()
   │
   ▼
stop(simplify)
   │
   ├─ TrackSimplifier.simplify(buffer)
   ├─ TrackStore.write(file, simplified)
   └─ 返回 File
```

### 6.2 内存策略

**全部驻留内存**：

```kotlin
private var buffer: MutableList<TrackPoint>? = null
```

**上限**：

```kotlin
companion object {
    private const val MAX_POINTS = 200_000  // 5 小时 @ 1Hz
}
```

**为什么不做流式写入？**

- 流式需要每次 append 时打开/关闭文件句柄
- 简化需要全局视角（Douglas-Peucker 看整条轨迹）
- 200,000 个 TrackPoint × ~64 bytes ≈ 12.8 MB 内存——现代手机可承受

**若未来需要更长记录**：
- 分段：每 1 小时刷盘一次
- 简化：分段简化 + 边界处理

### 6.3 记录流程

```kotlin
fun record(loc: Location) {
    val buf = buffer ?: return          // 未 start，忽略
    if (buf.size >= MAX_POINTS) return  // 达到上限，忽略

    // 1. 构建 TrackPoint
    val point = TrackPoint(
        lat = loc.latitude,
        lng = loc.longitude,
        altitudeM = if (loc.hasAltitude()) loc.altitude else null,
        speedMps = if (loc.hasSpeed()) loc.speed else null,
        bearingDeg = if (loc.hasBearing()) loc.bearing else null,
        accuracyM = if (loc.hasAccuracy()) loc.accuracy else null,
        timestampMs = System.currentTimeMillis(),
        elapsedNanos = if (loc.elapsedRealtimeNanos != 0L) loc.elapsedRealtimeNanos
                       else loc.time * 1_000_000L,
    )

    // 2. 入口过滤
    val lastKept = buf.lastOrNull()
    if (!filter.shouldKeep(point, lastKept)) {
        rejectedCount++
        return
    }

    // 3. 保留
    buf.add(point)
}
```

**关键点**：
- `lastKept` 用 `buf.lastOrNull()`（最后一个保留点），而非上一次 fix
- 若 rejected，不影响 `lastKept`——保证基准稳定

### 6.4 停止与简化

```kotlin
fun stop(simplify: Boolean = true, simplifyEpsilonM: Double = 0.5): File? {
    val buf = buffer ?: return null
    buffer = null                       // 立即清空引用（防重入）
    val file = targetFile ?: return null
    targetFile = null

    if (buf.size < 2) return null       // 少于 2 个点无意义

    val out = if (simplify) {
        TrackSimplifier.simplify(buf, simplifyEpsilonM)
    } else {
        buf
    }

    TrackStore.write(file, out)
    return file
}
```

**为什么 `stop` 后 buffer 置 null？**
- 防止并发调用 `record`
- 允许 `start` 重新初始化

## 7. Douglas-Peucker 简化

### 7.1 算法原理

**问题**：轨迹有 1000 个点，但很多点在同一直线上，删除它们不改变形状。

**核心思想**：递归地找"最能代表轨迹形状"的点。

```
算法步骤：
1. 保留起点 A 和终点 B
2. 找到 A、B 之间距离 AB 线段最远的点 C
3. 若 C 到 AB 的距离 > ε（容差），保留 C
4. 递归处理 AC 和 CB
5. 若距离 ≤ ε，丢弃中间所有点
```

**示意图**：

```
原始轨迹：
A ●━━━━━━━━━●━━━━━━━━━━━●━━━━━━━━━━● B
             ╲
              ●  C（偏离最远）

递归后：
A ●━━━━━━━━━●━━━━━━━━━━━●━━━━━━━━━━● B
              （C 保留）

若 C 到 AB 距离 < ε：
A ●━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━● B
    （中间点全部丢弃）
```

### 7.2 实现

```kotlin
object TrackSimplifier {
    fun simplify(points: List<TrackPoint>, epsilonM: Double = 0.5): List<TrackPoint> {
        if (points.size <= 2) return points
        val keep = BooleanArray(points.size)
        keep[0] = true
        keep[points.size - 1] = true
        douglasPeucker(points, 0, points.size - 1, epsilonM, keep)
        return points.filterIndexed { i, _ -> keep[i] }
    }

    private fun douglasPeucker(
        points: List<TrackPoint>,
        start: Int,
        end: Int,
        epsilonM: Double,
        keep: BooleanArray,
    ) {
        if (end - start < 2) return
        var maxDist = 0.0
        var maxIdx = -1
        val a = points[start]
        val b = points[end]
        for (i in start + 1 until end) {
            val p = points[i]
            val d = GeoMath.distanceToSegment(
                p.lat, p.lng,
                a.lat, a.lng,
                b.lat, b.lng,
            )
            if (d > maxDist) {
                maxDist = d
                maxIdx = i
            }
        }
        if (maxDist > epsilonM && maxIdx > 0) {
            keep[maxIdx] = true
            douglasPeucker(points, start, maxIdx, epsilonM, keep)
            douglasPeucker(points, maxIdx, end, epsilonM, keep)
        }
    }
}
```

**复杂度**：
- 平均：O(n log n)
- 最坏：O(n²)（极端锯齿状轨迹）

**对轨迹的场景**：真实 GPS 轨迹较平滑，平均复杂度表现良好。

### 7.3 容差选择

| ε | 效果 | 适用 |
|---|---|---|
| 0.2 m | 几乎不简化 | 高精度测绘 |
| **0.5 m** | **默认，保留转弯** | **通用** |
| 1.0 m | 明显压缩，丢失细微弯曲 | 长距离记录 |
| 2.0 m | 大幅压缩，只保留主干 | 概览显示 |
| 5.0 m | 极端压缩 | 只标起点终点 |

**默认 0.5 m 的选择依据**：
- 步行时每秒移动 1-1.5 m，0.5 m 容差能保留真实路径
- 驾车时每秒移动 15-30 m，0.5 m 几乎不简化——但驾车轨迹本来就是直线段
- 拐弯半径一般 5-10 m，0.5 m 容差不会抹平

### 7.4 实测效果

**步行 30 分钟**：
- 原始：1800 个点
- 简化后：约 400-600 个点（减少 70%）

**驾车 1 小时**：
- 原始：3600 个点
- 简化后：约 500-800 个点（减少 80%）

**静止 5 分钟**（含漂移）：
- 原始：300 个点（若未过滤）
- 入口过滤后：2-5 个点
- 简化后：2 个点（起点 + 终点）

## 8. 文件存储（TrackStore）

### 8.1 CSV 格式

```csv
# vela-track v1
# started 1696204800000
# ended   1696208400000
# points  1234
timestamp_ms,elapsed_nanos,lat,lng,alt_m,speed_mps,bearing_deg,accuracy_m
1696204800123,1234567890123,39.9091234,116.3976543,45.2,1.35,128.7,4.2
1696204802234,1234567891234,39.9091345,116.3976789,45.3,1.28,130.1,4.1
...
```

**格式说明**：

| 行 | 内容 |
|---|---|
| 头 4 行 | 注释（`#` 开头），含版本号、起止时间、点数量 |
| 第 5 行 | CSV 表头（列名） |
| 后续 | 每行一个 TrackPoint |

**为什么用 CSV？**
- **可读性**：用 Excel / 文本编辑器直接打开
- **可调试**：出现问题容易检查
- **通用性**：任何语言、任何平台都能解析
- **可分享**：直接发邮件/微信即可

### 8.2 写入

```kotlin
object TrackStore {
    fun write(file: File, points: List<TrackPoint>) {
        file.parentFile?.mkdirs()
        file.bufferedWriter().use { w ->
            w.write("# vela-track v1\n")
            w.write("# started ${points.firstOrNull()?.timestampMs ?: 0}\n")
            w.write("# ended ${points.lastOrNull()?.timestampMs ?: 0}\n")
            w.write("# points ${points.size}\n")
            w.write("timestamp_ms,elapsed_nanos,lat,lng,alt_m,speed_mps,bearing_deg,accuracy_m\n")
            for (p in points) {
                w.write("${p.timestampMs},${p.elapsedNanos},${p.lat},${p.lng},")
                w.write("${p.altitudeM ?: ""},${p.speedMps ?: ""},${p.bearingDeg ?: ""},${p.accuracyM ?: ""}\n")
            }
        }
    }
}
```

**空值表示**：`null` 写成空字段（两个逗号之间没东西）。

### 8.3 读取

```kotlin
fun read(file: File): List<TrackPoint> {
    if (!file.exists()) return emptyList()
    val out = ArrayList<TrackPoint>()
    file.bufferedReader().useLines { lines ->
        lines.forEach { line ->
            val t = line.trim()
            if (t.isEmpty() || t.startsWith("#") || t.startsWith("timestamp_ms")) return@forEach
            val parts = t.split(',')
            if (parts.size < 8) return@forEach
            runCatching {
                out.add(
                    TrackPoint(
                        lat = parts[2].toDouble(),
                        lng = parts[3].toDouble(),
                        altitudeM = parts[4].takeIf { it.isNotBlank() }?.toDouble(),
                        speedMps = parts[5].takeIf { it.isNotBlank() }?.toFloat(),
                        bearingDeg = parts[6].takeIf { it.isNotBlank() }?.toFloat(),
                        accuracyM = parts[7].takeIf { it.isNotBlank() }?.toFloat(),
                        timestampMs = parts[0].toLong(),
                        elapsedNanos = parts[1].toLong(),
                    ),
                )
            }
        }
    }
    return out
}
```

**容错**：
- 忽略注释和表头
- 字段数不足时跳过该行
- 单行解析失败时静默跳过（不中断整条轨迹的读取）

### 8.4 文件命名

```kotlin
fun newFile(dir: File, nameHint: String? = null): File {
    val stamp = java.text.SimpleDateFormat("yyyyMMdd-HHmmss", java.util.Locale.US)
        .format(java.util.Date())
    val safe = nameHint?.replace(Regex("[^A-Za-z0-9_-]"), "_")?.take(24) ?: "track"
    return File(dir, "$safe-$stamp.csv")
}
```

**命名格式**：`{nameHint}-{yyyyMMdd-HHmmss}.csv`

**示例**：
- `morning-ride-20261002-071523.csv`
- `track-20261002-180000.csv`

**为什么加时间戳？**
- 同一天可能记录多次
- 时间戳保证唯一性
- 排序时自动按时间顺序

**nameHint 净化**：
- 中文/emoji 会被替换为 `_`
- 长度限制 24 字符
- 防止路径穿越攻击

### 8.5 目录管理

```kotlin
fun list(dir: File): List<File> =
    dir.listFiles { f -> f.isFile && f.name.endsWith(".csv") }
        ?.sortedByDescending { it.name }
        .orEmpty()
```

**按文件名倒序** = 按时间倒序（因为文件名含时间戳）。

## 9. 轨迹回放（TrackPlayer）

### 9.1 时间轴设计

**关键**：按 `elapsedNanos` 的**时间间隔**回放，而非按数组索引。

```kotlin
fun play(): Flow<TrackPoint> = flow {
    val points = TrackStore.read(file)
    if (points.isEmpty()) return@flow
    var lastNanos = points.first().elapsedNanos
    emit(points.first())
    for (i in 1 until points.size) {
        val p = points[i]
        val dtNanos = p.elapsedNanos - lastNanos
        val waitMs = (dtNanos / 1_000_000L) / speedup.toLong()
        if (waitMs > 0) delay(waitMs)
        emit(p)
        lastNanos = p.elapsedNanos
    }
}
```

**为什么用 elapsedNanos 而非 timestampMs？**
- 墙钟可能因 NTP 同步跳变
- 单调时钟保证时间间隔准确
- 不受用户改时间影响

### 9.2 速度倍率

| speedup | 效果 | 用途 |
|---|---|---|
| 1x | 真实速度 | 复盘细节 |
| 3x | 3 倍速 | 快速浏览 |
| 10x | 10 倍速 | 长时间轨迹快速过一遍 |
| 0.5x | 半速 | 慢动作研究 |

**实现**：`waitMs = realDt / speedup`。

### 9.3 时长估算

```kotlin
fun durationSeconds(file: File, speedup: Float = 1f): Long {
    val points = TrackStore.read(file)
    if (points.size < 2) return 0
    val totalNanos = points.last().elapsedNanos - points.first().elapsedNanos
    return (totalNanos / 1_000_000_000L) / speedup.toLong()
}
```

**用途**：UI 显示"回放需要约 X 秒"。

## 10. 与 LocationTracker 集成

### 10.1 记录点位置

**关键：在 `processFix` 的最开头调用 `recorder?.record(loc)`**：

```kotlin
private fun processFix(loc: Location): Fix? {
    // ...
    
    // ★ 最优先：记录原始 fix
    recorder?.record(loc)
    
    // 然后才是位置过滤
    // ...
    val here = sanitizer.sanitize(...)
    // ...
}
```

**为什么在最前？**
1. **记录的是原始 `Location` 对象**，不是过滤后的 `LatLng`
2. **即使后续 filter 拒绝了这个 fix**（比如 outlier），轨迹记录也已独立判定
3. **即使位置过滤抛异常**，轨迹也已经记录

### 10.2 公开 API

```kotlin
class LocationTracker {
    private var recorder: TrackRecorder? = null

    /** 开始记录轨迹。 */
    fun startRecording(dir: File, nameHint: String? = null) {
        recorder?.stop()  // 若已在记录，先停止
        recorder = TrackRecorder(dir).apply { start(nameHint) }
    }

    /** 停止记录并保存。返回写入的文件。 */
    fun stopRecording(simplify: Boolean = true): File? {
        val file = recorder?.stop(simplify)
        recorder = null
        return file
    }

    /** 当前已保留的点数。 */
    fun recordedPoints(): Int = recorder?.size() ?: 0

    /** 当前已拒绝的漂移点数。 */
    fun rejectedPoints(): Int = recorder?.rejected() ?: 0

    /** 是否正在记录。 */
    val isRecording: Boolean get() = recorder?.isRecording == true
}
```

### 10.3 生命周期清理

```kotlin
fun stop() {
    // ... 停止其他组件 ...
    recorder?.discard()  // 未保存就销毁
    recorder = null
    reset()
}
```

**`discard()` 而非 `stop()`**：应用销毁时用户可能不希望自动保存——由调用方决定（通过 `stopRecording()`）。

### 10.4 线程安全

| 方法 | 调用线程 | 说明 |
|---|---|---|
| `record(loc)` | Main（LocationListener 回调） | 由 `processFix` 主线程调用 |
| `startRecording()` | 任意 | 由 Compose effect 或外部 API 调用 |
| `stopRecording()` | 任意 | 由 Compose effect 或外部 API 调用 |
| `recordedPoints()` | 任意 | 只读 |

**当前实现未加锁**：

- 若 `record` 与 `stop` 并发 → buffer 被置 null，`record` 里的 `?: return` 保护住
- 若 `record` 与 `start` 并发 → 新 buffer 覆盖旧 buffer，旧数据丢失（预期行为）
- 若 `recordedPoints` 与 `record` 并发 → 读到中间值，无害

**结论**：竞态存在但不致命。若要求严格，可加 `synchronized`。

## 12. 参数调优

### 12.1 常见调整需求

| 症状 | 调整 | 影响 |
|---|---|---|
| 静止时仍有大量点 | `TrackFilter.driftDistanceM` 8 → 15 | 更激进过滤漂移 |
| 步行时轨迹断断续续 | `TrackFilter.maxAccuracyM` 40 → 60 | 接受更差的精度 |
| 轨迹起点从漂移开始 | 先等 3 秒稳定再 `startRecording` | 起点准确 |
| 轨迹文件过大 | `simplifyEpsilonM` 0.5 → 1.5 | 更激进简化 |
| 轨迹丢失转弯细节 | `simplifyEpsilonM` 0.5 → 0.2 | 保留更多点 |

### 12.2 参数详解

#### `TrackFilter.maxAccuracyM`

- **含义**：超过此精度半径的 fix 直接拒绝
- **默认**：40 m
- **推荐**：
    - 城市：40（默认）
    - 郊区：30（GPS 更准）
    - 室内/桥下：60-80（放宽）
    - **禁用**：100+（等于不过滤）

#### `TrackFilter.driftDistanceM`

- **含义**：静止时超过此距离的移动判定为"疑似漂移"
- **默认**：8.0 m
- **推荐**：
    - 车载：15-20 m（车辆振动大）
    - 步行：5-8 m（人体噪声小）
    - 手机放包：10-15 m

#### `TrackFilter.driftStreakToAccept`

- **含义**：连续 N 次疑似漂移在同一区域就接受
- **默认**：3
- **推荐**：
    - 快速响应：2（1 秒内接受）
    - 保守：4-5（3-4 秒后接受）

#### `TrackSimplifier.simplifyEpsilonM`

- **含义**：Douglas-Peucker 容差
- **默认**：0.5 m
- **推荐**：
    - 存档：0.2 m
    - 通用：0.5 m（默认）
    - 分享：1.0-2.0 m
    - 概览：5.0 m

### 12.3 场景预设

**步行预设**：

## 14. 常见问题

### 14.1 轨迹点太多

**症状**：静止 1 分钟记录 50+ 点。

**原因**：
- `TrackFilter` 未启用
- 参数过松

**解决**：
```kotlin
TrackFilter(
    driftDistanceM = 15.0,      // 提高
    driftStreakToAccept = 5,    // 增加
)
```

### 14.2 轨迹点太少

**症状**：步行 5 分钟只记录 10 个点。

**原因**：
- `maxAccuracyM` 过严
- 自适应最小距离过大

**解决**：
```kotlin
TrackFilter(
    maxAccuracyM = 60f,         // 放宽
    stillSpeedMps = 0.3f,       // 降低
)
```

或检查 `speedMps` 是否一直为 0（若是，自适应阈值会偏大）。

### 14.3 轨迹形状不对

**症状**：轨迹绕过建筑物。

**原因**：**正常 GPS 现象**——多路径反射。

**解决**：
- 无法完全消除
- 提高 `maxAccuracyM` 严格度可以过滤部分
- 城市峡谷场景无法根治

### 14.4 文件过大

**症状**：1 小时轨迹 5 MB。

**原因**：未简化或简化不足。

**解决**：
```kotlin
tracker.stopRecording(simplify = true, simplifyEpsilonM = 1.0)
```

或事后重新简化：

```kotlin
val points = TrackStore.read(file)
val simplified = TrackSimplifier.simplify(points, 1.0)
TrackStore.write(newFile, simplified)
```

### 14.5 记录中途崩溃

**症状**：应用被杀，未保存的轨迹丢失。

**原因**：`stop` 未调用。

**解决**：加自动保存机制：

```kotlin
// 每 N 点自动保存快照
private var lastSnapshotSize = 0
fun record(loc: Location) {
    // ...
    buf.add(point)
    if (buf.size - lastSnapshotSize >= 100) {
        snapshot()  // 写临时文件
        lastSnapshotSize = buf.size
    }
}
```

**当前实现未包含**——若需要请扩展。

### 14.6 时间戳异常

**症状**：回放时快进/倒退。

**原因**：`timestampMs` 受 NTP 同步影响跳变。

**解决**：回放**只用 `elapsedNanos`**（当前实现已做）。若 CSV 里 `elapsedNanos` 为 0，回退到 `timestampMs`。

### 14.7 中文文件名乱码

**症状**：文件名为 `___-20261002.csv`。

**原因**：`newFile` 里的净化把非 ASCII 替换为 `_`。

**解决**：这是**故意的**——文件系统可能不支持某些字符。若需要中文文件名，修改 `newFile`：

```kotlin
val safe = nameHint?.replace(Regex("[/\\\\:*?\"<>|]"), "_")?.take(24) ?: "track"
```

只替换**路径不安全**字符，保留中文。

## 结束语

本系统在**简单性**和**正确性**之间取得了平衡：

- **简单性**：纯 Kotlin，无第三方依赖；接口清晰；参数可调
- **正确性**：多规则过滤覆盖常见漂移场景；Douglas-Peucker 保留形状；时间基准严格

**核心哲学**：

> 记录**原始**数据，**离线**简化。

轨迹记录是**数据采集**，不是**数据呈现**。让它在采集时保持纯净，在呈现时按需加工——这样既保证了数据的真实性，又保留了灵活性。
